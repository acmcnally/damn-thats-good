# ADR-0003: Authentication — WorkOS AuthKit, email OTP, rolling sessions

**Status:** Accepted (owner, 2026-08-28). Replaces two earlier takes on this ADR — `32854d8` (self-hosted Better Auth, session-based) and `f8124bb` (reopened, left open with a managed-provider lean). One open sub-item: the final session-lifetime numbers, to lock when wiring auth (Linear `DAMN-1`).
**Decision drivers:** product preference (auth is deliberately not a learning or maintenance surface) · scope & simplicity · external input (the Better Auth re-evaluation — the provider choice is kept revisitable on this basis)

## Context

The app needs accounts and login. Content is low-stakes (recipes, plus the email addresses used to sign in), and the app has no anonymous access, so auth exists mainly to tell users apart and to gate each book to its owners. Exposure of that data in a provider breach is an accepted risk.

This ADR has been revised twice. It began (`32854d8`) as *self-hosted Better Auth, session-based*, chosen when zero cost and self-hosting were assumed to be hard constraints. A later review reopened it (`f8124bb`): neither constraint was actually firm — "self-hosted" had come bundled with the Better Auth pick rather than being required on its own. That left a narrower, clearer requirement:

- **Auth should not be a thing to own.** Not a learning surface — there is ample service-tier learning in the recipe / book / versioning / search domain — and not a maintenance surface: no library to keep patched, no crypto to get right, no account-recovery plumbing to hand-build.
- **The configuration it does require should stay small and legible** — few enough moving parts to understand and audit, not a large console of interacting settings.
- **Cost:** every managed provider's free tier covers this project's scale (tens of users) indefinitely. The general preference for near-zero ongoing cost still applies; a small, controlled cost would be acceptable if it clearly earned its place.
- **A local `users` row exists regardless.** `RecipeVersion` authorship, Recipe Book ownership, and the 1:1 `Profile` all foreign-key to our own `User`. With a managed provider that row holds the provider's user id + email, created on first login; it holds no credentials.

Better Auth was reconsidered against that requirement and set aside — see Alternatives.

## Decision

- **Provider: WorkOS AuthKit, free tier.** Managed. Standard OAuth 2.0 / OIDC — a spec-compatible authorization server whose access tokens are JWTs verified against a per-client JWKS that WorkOS publishes.
- **Sign-in method (V1/V2): email OTP** (WorkOS "Magic Auth" — a six-digit single-use code, ~10-minute expiry). No password is stored and there is no password-reset flow to build.
- **Sign-in method (V3+): add Google OAuth** as a second option when non-owner users are onboarded. Identity-only scopes (`openid`, `email`, `profile`) — never sensitive or restricted Google scopes. Google is added as a WorkOS social connection; WorkOS supplies shared development credentials, and a project-owned Google Cloud OAuth client is added for production. Publishing that client to "In Production" (needed to clear the unverified-app screen and the test-user cap / 7-day refresh-token expiry) requires a privacy-policy URL, a homepage, and a verified domain — a V3 prerequisite, not V1 work.
- **Session model:** a short-lived access token (JWT, minutes) plus a rotating refresh token with reuse detection. The refresh / idle window is set generously (weeks to months) so an actively-used session effectively never prompts; a longer absolute cap (order of a year) still forces occasional re-auth so an abandoned or stolen logged-in device does not stay valid forever. When a session lapses, email OTP is the low-friction way back in. Revocation is server-side — end the session / invalidate the refresh-token family via the WorkOS API. The local `users` row is the app-side anchor; WorkOS holds session state.
- **Login UI:** hosted AuthKit on the free `*.authkit.app` subdomain, themed through the Branding settings (logo, favicon, brand colors, light/dark, corner radius) and global / per-page custom CSS. No custom domain in V1.
- **Email delivery:** WorkOS sends the OTP emails, from `access@workos-mail.com`, with SPF / DKIM / DMARC already configured on that domain. No email infrastructure on our side for V1/V2.
- **Frontend / backend wiring:** the React SPA uses the AuthKit React SDK (client-side code exchange, no server callback route required); the NestJS API validates the access-token JWT against the WorkOS JWKS. On first login (callback, or a `user.created` webhook) the API upserts the local `users` row, keyed by WorkOS user id and email. User-sync logic lives in the NestJS service as an ordinary API call — there is no vendor-hosted serverless code.

## Alternatives considered

- **Auth0 (managed).** The closest competitor, and the documented fallback (see Consequences). Rejected for V1 mainly on **configuration surface**: Auth0 spreads setup across Tenant, Application, API, Connection, Action, Branding, and Email-Provider objects, with session / token lifetime split across three levels (tenant idle / absolute, refresh-token idle / absolute + rotation, per-API access-token TTL) that constrain each other. Since this project deliberately wants a *non-default* long rolling session, that complexity is unavoidable rather than incidental. Auth0's free tier also has no dev/prod promotion (two disconnected tenants, which drift unless managed with its Terraform provider), does not include MFA, and — for passwordless specifically — its built-in email sender is test-only (low rate limit, silently drops excess, non-configurable from-address), so production email OTP would mean standing up a transactional email provider now. Auth0's one clear edge — a custom login domain on the free tier, which WorkOS charges for — only matters if a branded login URL is wanted in V1, and it is not.
- **Self-hosted Better Auth.** Rejected on the "not a thing to own" requirement: it is a young, fast-moving library with a pattern of frequent breaking changes across releases, so choosing it means signing up for an ongoing patch-and-upgrade treadmill — exactly what this decision is trying to avoid. Its recent track record has also included some fairly serious security issues; that is a secondary consideration, not the deciding one. (NestJS integration is also less-travelled than its Next.js path.)
- **Self-hosted mature options (Passport + argon2, Ory Kratos, Keycloak).** All technically sound, and would keep identity data fully local, but every one puts ongoing patching and operations on us — the burden the "not a thing to own" requirement rules out, once cost is not forcing the issue.
- **Clerk (managed).** Set aside for its proprietary embedded-component model, which is meaningfully harder to migrate away from than the standard-OIDC, hosted-page approach WorkOS and Auth0 share.
- **Magic-link passwordless (instead of OTP).** OTP was preferred: a code works regardless of which browser or device opens the email, whereas magic links fail when the link opens in a different browser than the one that started sign-in, and email security scanners can consume the single-use link before the user clicks it. WorkOS supports both; this is a configuration choice.

## Consequences

- **User identity and session state live at WorkOS**, not in our Postgres — the deliberate trade this decision makes: data locality for auth identity, in exchange for not owning that operational-security surface. All *user content* (recipes, books, versions, photos) and the `Profile` row stay in our own systems regardless; the "own your data" principle (ADR-0011) is about that content and is unaffected. The `users` row holds only the WorkOS user id + email.
- **Two cosmetic "built on WorkOS" tells**, both accepted for an invite-only audience: the login page is served from `*.authkit.app`, and OTP emails come from `workos-mail.com`. Removing either requires the WorkOS custom-domain add-on (~$99/mo) — a separate, optional future decision, not planned. Enabling a custom domain later changes the token `iss` claim and the JWKS URL, so it is a planned backend-config cutover (briefly accept both issuers, or force one re-auth — access tokens are short-lived, so old ones drain quickly); it does not touch user records.
- **No MFA in V1.** WorkOS's free tier includes MFA and passkeys, but V1 ships OTP-only, so control of a user's email inbox is control of their account. Accepted for this data. Passkeys are the natural first upgrade if the OTP round-trip becomes a friction point.
- **No password-reset flow** to build or maintain — a V1 scope reduction, not a gap.
- **One more external vendor**, alongside the ADR-0004 ingress vendor. A WorkOS outage means no one can log in, including the owner. Because the hosted login flow sends the OTP browser↔WorkOS, credentials never transit our own edge — this removes the plaintext-credential concern ADR-0004 raises, for the auth path.
- **Bringing email in-house later** (likely V3, when invites are built) does not require the paid custom domain: WorkOS can hand off delivery via the `magic_auth.created` webhook, letting the NestJS service send the OTP through its own provider. That is additive backend code and does not touch auth config, tokens, or sessions. The real cost of that move is email deliverability from a cold sending domain — use a dedicated sending subdomain, set SPF / DKIM / DMARC, use a real transactional provider, and don't cut over the same week new users are onboarded.
- **Fallback: Auth0**, if WorkOS materially changes its free-tier terms or its direction becomes a concern. Both are standard-OIDC hosted-page providers, so this is a re-integration (new SDK wiring, dashboard reconfiguration, `users` re-keyed by email — which we hold) rather than a data rescue, but it is not a config toggle. Keeping the provider choice revisitable is deliberate: it rests partly on external input, the lowest-weight driver.
- **Google OAuth is deferred, not designed against.** The `users` model must not hard-assume a single credential type, so V3 adds a provider / identity association rather than reworking the schema.
