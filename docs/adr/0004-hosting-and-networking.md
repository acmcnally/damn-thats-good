# ADR-0004: Hosting — self-hosted Proxmox + Docker Compose; public ingress TBD

**Status:** Accepted for compute, runtime, and storage (self-host on the existing Proxmox box). Open, before the app is exposed to the internet: (1) public ingress — Cloudflare Tunnel vs. Tailscale Funnel; (3) whether Caddy stays in the path or its routing folds elsewhere. Open, before photos ship (V3): (2) the Cloudflare free-plan photo-serving check. See Consequences.
**Decision drivers:** skill development (Proxmox / containers / Linux / deployment are project goals) · scope & simplicity (low, justified ongoing cost)

## Context

The maintainer runs a small self-hosted Proxmox box — a handful of cores, no SMT, limited RAM, an SSD plus slower bulk disks — already in use for local development. Strong preference to keep ongoing cost at or near zero (domain registration aside) — not an absolute gate, but paid infra has to clearly earn its place. App needs to be reachable by friends/family outside the home network.

**This is a deliberate learning area.** Getting hands-on with Proxmox, containerization, Linux administration, and end-to-end deployment is one of the project's explicit goals (see `CLAUDE.md`). So self-hosting on the existing box is the right call on learning grounds alone — a paid PaaS would *remove* that — and some of the friction below (LXC vs VM nuances, wiring a reverse proxy and a tunnel, running the DB yourself) is *expected and wanted*, not a cost to engineer away. The caution notes in this ADR exist to keep that friction from turning into data loss or a security hole — not to push toward a managed platform.

## Decision

- **Compute:** a separate container/VM on the same Proxmox box, distinct from the local dev environment, for production. **Pragmatic default: a full VM** — Postgres and Docker both run with less friction there, and unprivileged LXC has recurring gotchas around shared memory / `fuse` / nesting (worse when Docker runs *inside* LXC). A VM costs a little more RAM, acceptable for one small app on this box. **If the container-nuance practice is itself wanted**, running this in an LXC and working through those gotchas is a legitimate deliberate experiment — just make it a conscious choice, not a default. *(This experiment now lands on the **staging** environment, which is an LXC — ADR-0010 § Environments. Prod stays a VM.)*
- **Runtime:** Docker Compose. Postgres + the NestJS API are settled. The edge pieces are **provisional**: Caddy as an internal reverse proxy (routing `/api/*` vs. the static frontend) *if* it stays near-zero-config (see Consequences), and `cloudflared` *pending* the Cloudflare-vs-Tailscale decision below.
- **Storage:** SSD hosts the OS and Postgres data directory (latency-sensitive); the platter HDDs host recipe photo storage and *local* backup staging. Note: backups written only to a second disk **in the same box** protect against accidental deletion and nothing else (PSU failure, disk failure, theft, fire, ransomware = total loss). An off-site copy is required — see ADR-0009.
- **Public access (leaning, not locked):** Cloudflare Tunnel — `cloudflared` opens an outbound-only connection from the server to Cloudflare, no inbound ports on the home router, no dynamic DNS. Cloudflare terminates TLS at their edge. **Tailscale Funnel is a live alternative** — see Alternatives; decide before first internet exposure.
- **Domain:** registered with a third-party registrar. If Cloudflare Tunnel wins, DNS nameservers delegate to Cloudflare (all-or-nothing — see Consequences); Tailscale Funnel would not require that.

## Alternatives considered

- **Traditional port forwarding + DDNS + Caddy/Let's Encrypt**: the "DIY" path the owner originally assumed. Works, but exposes an open inbound port on the home network (larger attack surface) and fails outright if the ISP uses CGNAT (no real public IP). Rejected in favor of the tunnel's outbound-only model.
- **Tailscale**: the original ADR only considered the mesh-VPN model (every visitor must be added to the tailnet) and dismissed it on that basis. That dismissal is now considered too quick: **Tailscale Funnel** serves a private service to the *public* internet over HTTPS with no requirement that visitors join the tailnet — which is exactly the stated need. Funnel keeps ingress inside one vendor the owner already wants for personal admin access, has hobbyist-friendly terms, and avoids delegating the whole domain's DNS. Trade-offs vs. Cloudflare Tunnel: Funnel currently allows only a small fixed set of ports, has bandwidth expectations aimed at low-traffic use, and routes through Tailscale's relays. **This deserves a real head-to-head before the app is first exposed to the internet**, rather than defaulting to Cloudflare. (Note "public internet" here means network-reachable from outside the home LAN — the app itself always sits behind authentication; see CLAUDE.md.) Cloudflare Tunnel remains the leaning for now only because of its maturity and the already-written config.
- **ngrok**: same tunnel category as Cloudflare Tunnel, but its free tier is aimed at temporary dev tunnels; a paid tier for permanent use buys nothing over Cloudflare Tunnel or Tailscale Funnel, which do the job for free.
- **Self-hosted tunnel software (FRP, Pangolin)**: fully self-owned alternative to trusting Cloudflare as a middleman, but requires renting and maintaining a separate VPS with a real public IP — a recurring cost and a box to babysit for no benefit over the free tunnel options.

## Consequences

- Cloudflare sees decrypted (plaintext) traffic at their edge before re-encrypting to the origin. This is **not** just "low-sensitivity recipe data" — it includes the session token on every authenticated request, plus exposure to a compromised Cloudflare account, a malicious insider, or legal compulsion. This cuts against the general preference to keep credentials flowing only through systems we control. Accepted for now given the free, low-maintenance benefit and the hobby scale, but it is a genuine reason to weigh Tailscale Funnel (fewer parties in the plaintext path, no full-domain DNS delegation) — see Alternatives. Note: sign-in itself runs browser↔WorkOS (ADR-0003's hosted OTP flow), so login credentials never transit our Cloudflare edge — only the session token issued afterward does.
- **Cloudflare free-plan terms vs. a photo-heavy app.** Cloudflare's Self-Serve Subscription Agreement restricts using the CDN/proxy to serve a disproportionate amount of non-HTML content (large images, video, file downloads) on the free plan; zones have historically been flagged for this. A recipe app serves user-uploaded photos on nearly every page. Mitigations: photos are downscaled on upload and served only as small renditions (ADR-0008 — needed anyway), and be ready to move photo serving to a different path (direct via Funnel, or a separate host) if Cloudflare ever objects. Not a live concern until photos ship (V3). This risk is **accepted but must be monitored**, not ignored.
- Changing the domain's nameservers to Cloudflare means *all* DNS records for the domain (not just this app) are managed through Cloudflare's dashboard going forward, not the current registrar's — a one-time, all-or-nothing move per domain.
- No open ports on the home router at all — meaningful reduction in attack surface vs. the traditional approach.
- **Proxy-hop count / Caddy's role.** The path is Cloudflare edge → `cloudflared` → Caddy → app. Caddy's headline feature (automatic Let's Encrypt TLS) is redundant here because Cloudflare terminates TLS, so Caddy is doing only `/api` vs. static-asset routing. That is worth keeping only if it stays near-zero-config; if it grows fiddly, fold the routing into the API framework or the `cloudflared` ingress rules and drop Caddy.
- **Vendor concentration.** Delegating nameservers to Cloudflare puts DNS (for the whole domain, all-or-nothing), TLS, and sole ingress in one provider. A Cloudflare account ban, outage, or free-tier policy change takes the app fully offline. This is the main argument for the Tailscale Funnel evaluation above, and a reason to keep *other* external dependencies minimal.
